- новости из официального Telegram-канала с изображениями и форматированием;

- мастер подключения Happ и INCY для основных платформ;
- уникальные SEO-метаданные и social-preview для всех публичных страниц;
- автоматическая проверка качества, аварийные состояния и усиленная production-конфигурация.

## VPS-развёртывание

Production-конфигурация для Ubuntu и Caddy хранится в `ops/vps`. Сервер автоматически проверяет ветку `main`, собирает новый коммит в отдельном каталоге, переключает релиз только после успешной сборки и возвращается к предыдущему релизу, если локальная health-проверка не проходит.

Публичный интерфейс цифровой экосистемы «Технологии • Сервисы • Возможности».

## Архитектурное направление

Проект развивается как публичный сайт на Next.js с App Router. UI находится в `app` и `src/components`, продуктовые сценарии — в `src/features`, контент и внешние клиентские ссылки — в `src/config`. Личный кабинет и Telegram-бот остаются самостоятельными связанными сервисами; сайт не дублирует их авторизацию или интерфейс.

Внешние интеграции всегда вызываются только с сервера. Отсутствующие API не подменяются случайными числами или фиктивными записями.

### Мониторинг

`/api/status` проверяет сайт, кабинет и Telegram, а затем возвращает браузеру только безопасную сводку. Для реального процесса бота задайте закрытый `STATUS_BOT_HEALTHCHECK_URL`. Подключение Remnawave выполняется через `REMNAWAVE_BASE_URL`, серверный `REMNAWAVE_API_TOKEN` и настраиваемый путь `REMNAWAVE_NODES_PATH`.

Локации задаются JSON-массивом в `STATUS_LOCATIONS_JSON`. Для каждой локации можно указать независимый `probeUrl` и `remnawaveUuid`: если источники расходятся, интерфейс показывает частичные ограничения вместо ложного состояния «всё работает». Эти значения и токен не попадают в публичный ответ API.

## Локальный запуск

1. Установить Node.js 22.13+ и pnpm.
2. Скопировать `.env.example` в `.env` и заполнить только доступные значения.
3. Выполнить `pnpm install`.
4. Выполнить `pnpm dev`.

Полная проверка перед релизом: `pnpm release:check`. Дополнительные шаги находятся в `RELEASE_CHECKLIST.md`, история изменений — в `CHANGELOG.md`, порядок сообщения об уязвимостях — в `SECURITY.md`.

Перед production-запуском необходимо заполнить доступные серверные переменные окружения. Токены и другие секреты не должны храниться в репозитории.

## Ветки разработки

Стабильный сайт развёртывается из `main`. Новые функции сначала собираются и проверяются в `dev`, а после приёмки переносятся в `main` через pull request. Подробный порядок описан в `CONTRIBUTING.md`.
